# 亮点一：多 Agent 规划、协作与局部修复

> 这一篇回答四个问题：为什么拆 Agent、怎样通信、怎样并行、失败后为什么不是全部重跑。

## 1. 业务问题不是“多放几个 Agent”

跨品类组合选购同时涉及预算、多个商品槽位、库存和兼容性；设备排查需要在每轮用户反馈后继续；售后分析还要读取本人订单和当前政策。让一个模型拥有所有数据和工具会出现三个问题：权限过大、失败难定位、关键规则容易被自然语言推理覆盖。

项目按“信息来源 + 工具权限 + 输出责任”拆成四类任务角色：

| 角色 | 主要职责 | 不能做什么 |
| --- | --- | --- |
| Coordinator | 整理目标、提出计划、组织最终结果 | 不直接读写购物车或订单 |
| Catalog Analyst | 查 SKU、库存、兼容规则、本人订单，执行确定性组合求解 | 不用文档旧价格覆盖 Catalog |
| Evidence Researcher | 按业务范围查商品说明、兼容资料和政策 | 不扩大商品范围，不执行业务写入 |
| Reviewer | 检查需求覆盖、规则结果、解释和引用 | 不能把硬规则失败改成通过 |

角色不等于四个独立模型。Catalog 查询和组合计算主要是确定性能力；Planner 与 Reviewer 可以调用模型。这样既有 Agent 的动态性，又保留购物规则的可验证性。

## 2. 两种编排为什么同时存在

### 2.1 LangGraph 同步协作图

普通 Chat 请求在一次 HTTP 生命周期内完成。LangGraph Supervisor 根据请求选择 Product、RAG、Saved Preference 和 Decision 节点。图状态承载当前请求、角色结果和下一跳，最终由 Decision 节点汇总。

适用例子：查询某个商品、比较已知商品、根据当前候选查说明。

### 2.2 PostgreSQL 持久化任务 DAG

组合选购、排查和售后任务可能需要多次模型调用、等待用户、执行数分钟或在进程重启后继续。它们使用 `GoalSpec → PlanProposal → Steps`，把 DAG 保存到 PostgreSQL，由独立 Worker 领取。

适用例子：三件套组合、五轮以内的连接排查、读取订单后等待用户补充“是否拆封”。

这不是重复造轮子。LangGraph 解决一次请求中的状态流转，持久化 DAG 解决跨请求、跨进程和等待人类的生命周期。

## 3. Planner 怎样工作

系统先把用户目标转换成 `GoalSpec`。Planner 有两种模式：

- offline：使用可重复的确定性计划，适合默认运行、测试和模型不可用时降级；
- agent：通过 Model Gateway 调用模型，提出步骤、依赖和简短理由。

模型只看到允许的业务能力，输出后还要经过服务端投影和验证。服务端不会信任模型返回的 capability、role、owner 或 endpoint，而是按已注册的基线步骤恢复可信字段，只接受可能的步骤顺序和依赖建议。

计划验证包括：

1. 最多 12 个步骤；
2. capability 必须属于只读白名单；
3. role 与 capability 必须匹配；
4. 依赖节点必须存在；
5. DAG 不能有环；
6. 根节点并行前沿不能超过 3；
7. 必须包含 `verify_result`；
8. 模型不能加入支付、任意代码或外部 URL。

因此模型做的是“受约束计划提案”，不是拥有无限工具的自主控制器。

## 4. Agent 之间怎样通信

当前不是 Agent 互发自然语言消息，也不用 MQ。计划步骤通过结构化合同交接：

- `GoalSpec`：当前目标、硬条件、软要求、锁定选择、排除项和缺失问题；
- `PlanStep`：步骤 key、角色、能力、依赖、输入引用和输出类型；
- `StepResult`：步骤身份、状态、结构化输出、证据版本、usage 和错误码；
- `Artifact`：不可变中间产物、输入指纹、来源和验证状态；
- `VerificationReport`：状态、问题、受影响步骤/SKU/产物和允许修复动作。

结构化合同解决字段缺失、角色越权和结果归属问题。它不能自动保证业务内容正确，所以后面仍需 Catalog、证据和规则验证。

## 5. 有界并行是怎样实现的

Worker 每次查找依赖已经全部完成的步骤，形成 ready frontier，最多领取三个。每个步骤使用独立数据库 Session 执行，避免不同分支共享 ORM 状态。完成时使用 task id、plan revision、step lease token 和输入指纹提交。

例如组合任务：

```text
extract_goal
├─ catalog_candidates
│  └─ lookup_compatibility
│     └─ solve_bundle
└─ retrieve_evidence

solve_bundle + retrieve_evidence
└─ verify_result
   └─ compose_result
```

`catalog_candidates` 和 `retrieve_evidence` 在目标明确后可以并行；`solve_bundle` 必须等待候选和兼容事实；验证必须等待业务方案与证据。并行由依赖决定，不由“Agent 数量”决定。

并行难点是两个 Worker 可能同时看见同一步。项目使用 PostgreSQL 行锁、`SKIP LOCKED`、任务 scheduler epoch、步骤 lease token 和条件提交。拿到旧 token 的迟到结果会被 fencing 拒绝。

## 6. 为什么需要 Reviewer，而且为什么规则先执行

验证分两层：

### 确定性规则

负责能够明确计算的事实：

- 组合总价是否超过预算；
- 币种是否一致；
- 是否存在可验证方案；
- 兼容状态是否为 supported；
- 售后订单和政策事实是否足够；
- 关键证据是否可用。

### 模型 Reviewer

负责更适合语言理解的问题：

- 解释是否覆盖用户目标；
- 引用是否真正支撑文字结论；
- 是否漏掉必要说明；
- 是否还需要用户信息。

合并时规则具有更高权威。规则已经判为 `repairable/needs_input/rejected` 时，模型说 `pass` 也不能覆盖；规则通过后，模型可以提出更严格的问题，但不能修改价格、库存和权限。

## 7. 局部修复为什么比全部重跑更好

假设组合已经算出，但证据通道临时不可用。最简单的实现是整个任务从头执行，这会重复查询 Catalog、增加模型和数据库成本，还可能因库存变化得到完全不同候选。

项目根据 `VerificationIssue.affected_steps` 计算依赖后代：

```text
retrieve_evidence 失败
→ 失效 retrieve_evidence
→ 失效 verify_result
→ 失效 compose_result
→ 保留 catalog_candidates / compatibility / solve_bundle
```

系统创建新的 Plan revision，旧步骤标记 superseded；未受影响且输入、证据和可售事实仍有效的产物可以复用。修复次数最多两次，超过后进入等待、降级或终止，防止“反思—重试—反思”死循环。

这里的重试与修订不同：网络超时重试的是同一步同一意图；业务修订是因为验证发现方案本身需要改变，会产生新的 plan revision。

## 8. 三类任务为什么计划不同

### 组合选购

重点是多槽位候选、兼容规则、组合求解和预算验证。每槽最多 5 个候选，最多评估 125 种组合，最终最多给 3 个方案。

### 兼容排查

重点是设备、症状、受信检查步骤和用户观察。一次只提出安全检查，等待用户反馈后继续，最多五轮；不能声称系统远程执行了物理检查。

### 售后分析

重点是 owner-scoped Order/Payment、当前政策和缺失事实。没有可信送达日期或拆封状态时只能返回 conditional/unknown；用户补充内容标记为 `user_reported`。

三个计划共享合同，但步骤和依赖不同，这比按关键词返回一份固定 JSON 更接近真正的任务规划。

## 9. 失败和终止怎样设计

任务不会无限执行。当前主要限制包括：

- 计划最多 12 步；
- 并行最多 3 步；
- 累计步骤尝试最多 36；
- 模型尝试最多 24；
- 局部修订最多 2 次；
- 用户交互最多 5 轮；
- 默认任务绝对过期 24 小时；
- 单角色结果和总 Artifact 有大小上限。

缺事实进入 `waiting_input` 并释放租约；取消、删除和过期通过 fencing 阻止迟到写入；模型不可用时显式记录 agent fallback，不把离线计划冒充模型成功。

## 10. 这项设计最难的地方

**难题一：模型计划不可信。** 解决方式是模型只提案，服务端投影可信能力并做 DAG/权限校验。

**难题二：并行执行会重复提交。** 解决方式是行锁、SKIP LOCKED、lease token、scheduler epoch 和条件完成。

**难题三：Reviewer 可能否定正确规则。** 解决方式是规则先行、Reviewer 只允许收紧、不允许覆盖规则失败。

**难题四：修复可能无限循环。** 解决方式是问题定位、局部失效、进展指纹和累计修订/尝试上限。

**难题五：模型调用很慢。** Worker 在调用期间使用独立会话续租，返回前刷新数据库状态，再用 token fencing 保存；超时进入 Gateway 熔断和降级。

## 11. 面试追问与回答

**为什么不使用纯 ReAct？** 购物任务有明确预算、库存和权限边界。纯工具循环难以保证最大步骤、恢复和原子动作，因此采用外层计划/DAG，模型只在受控位置参与。

**为什么不用 LangGraph checkpoint 直接恢复？** 同步 Chat 已使用 LangGraph。任务工作台还要支持独立 Worker、多实例领取、行级竞态、任务列表和业务事件，数据库表能直接表达这些生产语义。

**多 Agent 的价值怎样证明？** 当前能证明权限隔离、失败定位、分支并行和局部恢复；不能凭角色数量声称准确率提升。质量收益需要同模型同数据对照实验。

**Agent 之间是否用 Redis？** 不用。任务事实在 PostgreSQL；Redis 是可选的跨实例 admission、rate limit、dedup 和 cache 协调。

## 12. 30 秒口述

> 我没有让多个 Agent 自由聊天，而是按商品、证据和验证职责划分能力。普通对话由 LangGraph 路由，复杂任务先生成白名单内的计划并持久化成 DAG。Worker 按依赖领取最多三个只读步骤，结果通过结构化合同和不可变产物交接。规则先验证预算和兼容性，模型 Reviewer 只能补充解释问题；失败时只重跑受影响步骤和后继节点，最多修订两次，避免全量重跑和死循环。
