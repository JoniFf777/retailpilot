# ShopMind 项目通俗介绍：这个项目做了什么，为什么这样做

> 这是一份用于理解项目和准备面试的说明。先讲业务，再讲技术。看完后至少应该能回答三个问题：这个项目是什么、解决了哪些难题、我在简历和面试里应该怎么讲。

理解业务后，可以继续阅读 [项目目录结构详解](D:/python/retailpilot/docs/shopmind_directory_structure_guide.md)，了解每个模块在代码中的位置和调用关系。

## 一、先用一句话说清楚项目

**ShopMind 是一个面向消费电子产品的智能选购与交易系统。用户可以用自然语言描述需求，系统会分析预算和配置要求，推荐具体 SKU 并给出理由和资料依据；用户确认后，还可以继续完成加购、结算、创建订单、库存预占和模拟支付。**

它可以理解为一个简化版的“京东/淘宝智能导购助手”，但项目重点不是页面或商品数量，而是研究：

> 怎样把大模型和 Agent 的不确定回答，安全地接入价格、库存、购物车、订单和支付这些必须准确的业务系统。

所以这不是一个只会聊天的机器人，也不只是一个普通电商后台。它由两部分组成：

1. **智能导购部分**：理解用户需求、搜索商品、查询文档和政策、读取用户偏好、生成推荐。
2. **交易系统部分**：确认加购、购物车、结算、订单、库存、模拟支付和业务事件。

## 二、用户实际怎么使用这个项目

假设用户输入：

> “我想买一台 6000 元以内的笔记本，至少 16GB 内存，重量不要超过 1.5kg，平时主要写代码。”

系统会执行下面这条链路：

```mermaid
flowchart LR
    A[用户自然语言需求] --> B[解析预算、品类和配置]
    B --> C[从数据库筛选可售 SKU]
    C --> D[结合用户偏好排序]
    D --> E[查询商品说明和政策资料]
    E --> F[返回 1～3 个推荐和理由]
    F --> G[用户选择具体 SKU]
    G --> H[生成待确认操作]
    H -->|用户确认| I[加入购物车]
    I --> J[结算预览]
    J --> K[创建订单并预占库存]
    K --> L[模拟支付]
```

具体来说：

1. 系统识别出这是“笔记本推荐”，预算上限是 6000 元，内存和重量是必须满足的条件。
2. 从 PostgreSQL 商品目录里寻找仍在销售、有库存、价格和配置都满足要求的具体 SKU。
3. 对候选商品进行可解释排序，例如内存、重量、价格和用户已确认的品牌偏好分别贡献多少分。
4. 从商品说明和售后政策中检索相关资料，为推荐补充引用；查不到时会明确告诉用户证据不足。
5. 返回最多 3 个推荐，并展示具体配置、匹配原因、分项评分和资料引用。
6. 用户说“选第二个”时，系统会把它解析成当前候选列表中的具体 SKU。
7. 系统不会立即写购物车，而是先展示一个待确认操作。只有用户确认后才加购。
8. 后续可以预览结算金额、创建订单、预占库存并执行模拟支付。

如果下一轮用户说“预算提高到 7000，第二个不要”，系统不会重新猜整段聊天记录，而是在上一轮结构化状态上修改预算并排除指定 SKU。

## 三、这个项目包含哪些模块

### 1. Web 前端

前端使用 React 和 TypeScript，提供：

- 对话式商品推荐；
- 商品目录和 SKU 详情；
- 商品对比；
- 待确认操作；
- 购物车和结算；
- 订单列表、订单详情和模拟支付；
- 用户记忆与隐私数据管理；
- Agent 运行记录和服务状态。

### 2. FastAPI 后端

后端负责 API、身份校验、业务服务和数据库事务。主要接口覆盖：

- 对话和流式事件；
- 商品目录和推荐结果；
- 待确认操作与购物车；
- 结算、订单和支付；
- 用户数据检查、修改和删除；
- 健康检查和运行状态。

### 3. 多 Agent 推荐系统

系统中有几个职责分离的只读角色：

| 角色 | 职责 |
| --- | --- |
| Supervisor | 判断用户意图，决定需要哪些能力 |
| Product Agent | 查询商品、价格、库存和商品详情 |
| RAG Agent | 查询商品说明、保修、退货等文档 |
| Preference Agent | 读取用户已经确认的偏好 |
| Decision Agent | 汇总信息并组织回答，不执行写操作 |

它们不是五个随意聊天的大模型，而是一组有明确输入、输出和权限边界的执行节点。默认关键路径可以确定性运行，便于测试和复现。

### 4. 推荐引擎

推荐引擎负责真正决定“哪些商品可以推荐、谁排在前面”。它包括：

- 中文预算和配置条件解析；
- 10 类消费电子的品类 Schema；
- 硬约束过滤；
- 用户偏好软排序；
- 分项评分和推荐解释；
- 多轮购物状态；
- 商品与政策证据检索。

### 5. 交易系统

交易部分包括：

- SKU 级购物车；
- 带签名的结算快照；
- 幂等订单创建；
- 库存预占、支付扣减、取消和超时释放；
- 模拟支付和失败恢复；
- Transactional Outbox 业务事件。

### 6. Agent Runtime 与工程保障

这一层不是用户直接看到的功能，作用是让 Agent 可以被安全运行和排查：

- 保存每次运行及其事件；
- 限制运行时间、步骤和工具调用次数；
- 支持请求幂等和结果重放；
- 控制不同 Agent 可以调用哪些工具；
- 通过 SSE 向前端发送执行阶段；
- 记录安全审计和健康指标；
- 支持本地或 Redis 协调。

## 四、项目最值得讲的 5 个亮点

### 亮点一：不是让大模型直接决定一切，而是“Agent + 确定性规则”结合

自然语言适合交给模型理解，但价格、库存和配置是否满足条件，不能由模型猜。

项目将职责拆开：

- Agent 负责理解问题、选择只读任务和解释结果；
- Category Schema 负责定义每种商品有哪些属性、单位和合法范围；
- PostgreSQL Catalog 负责价格、SKU 和库存真值；
- 排序器负责可复现的过滤和加权评分。

例如用户要求“重量不超过 1.5kg”，这是硬约束。一个 1.8kg 的商品即使其他配置再好，也不能通过增加其他分数进入结果。

这个设计解决了推荐结果不可控、难以解释、难以回归测试的问题。

### 亮点二：多轮对话不是简单拼接历史消息，而是维护结构化购物状态

简单聊天机器人通常把历史对话全部交给模型重新理解，容易出现：

- 用户只修改预算，系统却丢失之前的内存要求；
- 用户明确删除一个条件，旧条件下一轮又被恢复；
- 两个请求同时完成，旧结果覆盖新状态；
- 用户说“第二个”，却选中了已经更新后的另一件商品。

项目为每个用户和对话保存 `ShoppingSessionState`，只修改本轮明确变化的字段。状态带版本号，写入数据库时使用乐观并发控制；候选序号会过期，避免引用旧列表。

这使多轮购物对话变成一个规则清楚的状态机，而不是依赖模型每次重新猜测上下文。

### 亮点三：RAG 只提供证据，不能篡改商品事实

RAG 容易出现检索到无关文档、旧政策或错误商品说明的问题。项目对此设置了边界：

- 价格、库存和 SKU 身份只能来自结构化数据库；
- 商品文档只能绑定到当前候选商品；
- 产品资料和政策资料分开检索；
- 向量召回和关键词召回通过 RRF 融合；
- 政策会检查适用范围和版本；
- 检索失败时返回 `unknown`、`degraded` 或 `unavailable`，不把“没查到”包装成肯定答案。

也就是说，RAG 可以补充“为什么推荐”和“政策怎么规定”，但不能凭一段文档把一个没有库存的 SKU 变成可购买商品。

### 亮点四：Agent 不能直接写业务数据，所有副作用都要经过用户确认

如果让 Agent 直接调用“加入购物车”或“保存偏好”，模型误判一次就会产生真实副作用。

项目采用 Human-in-the-loop：

1. 读 Agent 只查询商品、文档和偏好；
2. 当用户表达加购意图时，先创建一个 `PendingAction`；
3. 前端展示准备执行的 SKU、数量和结果预览；
4. 用户确认后，后端再次校验归属、状态、有效期和参数；
5. 校验通过才执行写入，取消或过期则不产生副作用。

Tool Gateway 还会检查工具权限、参数、用户归属和调用预算。这样把“模型建议做什么”和“系统真正执行什么”隔离开。

### 亮点五：推荐之后还有完整的交易一致性设计

项目没有停留在“推荐三个商品”的演示，而是继续实现了购物车、订单、库存预占、模拟支付和 Outbox。

关键设计包括：

- Checkout 使用服务端签名快照，防止客户端修改价格或使用过期购物车；
- 创建订单时按稳定顺序锁定 SKU 库存，防止并发超卖和多 SKU 死锁；
- 下单先预占库存，支付成功后才真正扣减，取消或过期则释放；
- 订单和支付使用 Idempotency-Key 与请求 hash，处理重复点击和响应丢失；
- 支付渠道调用放在数据库事务外，避免网络等待长期占锁；
- 渠道成功后先保存 `provider_succeeded`，本地提交失败时可以恢复，而不会再次扣款；
- 业务状态和 Outbox 事件在同一事务中写入，避免订单成功但消息永久丢失。

这一部分体现的是后端交易系统能力，也是项目区别于普通 Agent Demo 的关键。

## 五、开发过程中遇到的问题，以及解决思路

### 问题 1：用户说的话很模糊，如何转成可执行条件？

**例子：**“六千左右，内存大一点，别太重。”

**难点：** 文本里包含模糊表达、中文金额、单位和比较关系，直接让模型推荐很难稳定复现。

**解决思路：**

- 先识别商品品类；
- 将预算、属性、比较符号和硬软约束转换成 Pydantic 结构；
- 用品类 Schema 校验单位、范围和枚举；
- 信息不足时返回澄清问题，而不是强行推荐。

**价值：** 后续筛选和排序面对的是结构化条件，结果稳定、可解释、可测试。

### 问题 2：多轮修改时，怎样避免上下文混乱？

**例子：** 第一轮要求 6000 元和 16GB，第二轮只说“预算改成 7000”。

**难点：** 第二轮既要保留 16GB，又不能把用户已经清除的条件从历史消息中恢复。

**解决思路：** 保存版本化购物状态；新一轮只生成字段 patch；显式区分新增、修改和清空；通过版本 CAS 阻止旧请求覆盖新状态。

**价值：** 多轮对话具有明确的合并和冲突规则。

### 问题 3：如何降低模型幻觉对推荐结果的影响？

**难点：** 模型可能编造价格、库存或参数；检索也可能返回无关文档。

**解决思路：**

- 数据库拥有商品事实；
- 硬约束和排序由确定性代码完成；
- RAG 只能给既有候选补充证据，不能添加新 SKU；
- 对证据设置商品范围、政策适用性和状态检查；
- 证据不足时明确降级或要求澄清。

**价值：** 模型的作用被限制在适合它的理解和表达范围内。

### 问题 4：如何防止 Agent 误操作购物车？

**难点：** 自然语言意图存在误判，写操作又不可随意执行。

**解决思路：** 读写权限分离，通过 PendingAction 保存准备执行的操作，让用户确认；确认时重新校验用户归属、SKU、数量、状态和有效期。

**价值：** 即使 Agent 理解错误，也不会直接造成购物车或偏好变化。

### 问题 5：两个用户同时抢最后一件库存怎么办？

**难点：** 两个请求可能都先读到“库存为 1”，然后同时下单。

**解决思路：** PostgreSQL 行锁和带条件的库存更新；下单时预占库存；多 SKU 按固定顺序加锁；任一项失败时整单回滚。

**价值：** 保证库存不会被超卖，同时避免多商品订单形成 AB/BA 锁顺序死锁。

### 问题 6：支付成功后，本地数据库更新失败怎么办？

**难点：** 如果直接重试整个支付请求，用户可能被重复扣款。

**解决思路：** 将支付拆成三段：先提交 PaymentAttempt claim；事务外调用渠道；单独保存渠道结果。渠道成功进入持久化的 `provider_succeeded` 状态，之后再完成本地订单、库存和事件更新。

**价值：** 本地最终提交失败后可以继续完成，而不必重新调用支付渠道。

### 问题 7：订单提交成功，但消息队列发送失败怎么办？

**难点：** 数据库事务和消息队列无法通过普通代码做到同一个原子提交。

**解决思路：** 在订单事务内同时写入 Outbox 记录；后台 worker 再领取并发布。使用租约、CAS、退避重试、死信和 redrive 处理崩溃及失败。

**价值：** 已提交的业务事件不会因为瞬时 MQ 故障永久丢失。

**边界：** 当前是至少一次发布，可能出现重复消息；Consumer、Inbox 和消费端去重尚未实现，不能称为端到端 exactly-once。

### 问题 8：Agent 运行失败时如何定位和复现？

**难点：** 多个节点、工具和重试混在一起，普通日志很难解释失败发生在哪一步。

**解决思路：** 使用统一 Harness 保存 Run、顺序事件、工具调用和使用量；为运行设置预算、超时、取消和幂等合同；通过确定性评测和 trajectory replay 验证关键生命周期。

**价值：** 可以回答一次请求经过了哪些步骤、使用了什么工具、在哪一步失败，以及重试会不会重复产生副作用。

## 六、这个项目的技术架构，用最简单的话讲

```text
React 前端
    ↓
FastAPI 接口
    ├── 对话推荐 → LangGraph / 推荐引擎 / RAG
    └── 交易接口 → Cart / Checkout / Order / Payment
                         ↓
PostgreSQL + pgvector
    ├── 商品、SKU、价格和库存
    ├── 对话、运行、记忆和文档向量
    └── 购物车、订单、支付和 Outbox

可选组件：
Redis       → 多实例准入、限流、去重和缓存
RocketMQ    → Outbox 事件异步发布
LangSmith   → 显式启用时做云端 Trace / Evaluation
```

这是一套模块化单体架构。Agent 默认在同一个后端进程内协作；Redis、远程 Agent 适配和 RocketMQ 都是可选扩展。简历中不要把它描述成已经上线的微服务集群。

## 八、简历可以写成这 5 点

项目名称建议：**ShopMind｜智能购物决策与交易 Agent 系统**

项目简介建议：**面向中文消费电子选购的全栈 Agent 系统，将自然语言需求转换为可解释的 SKU 推荐，并通过人工确认衔接购物车、订单、库存预占和模拟支付。**

技术栈：**FastAPI、LangGraph、Pydantic、SQLAlchemy、PostgreSQL/pgvector、React/TypeScript；可选 Redis、RocketMQ。**

简历要点候选：

1. 基于 LangGraph 构建 Product、RAG、Preference、Decision 等职责分离的只读 Agent 流程，将中文预算和配置需求转换为结构化约束，结合 Category Schema 完成 SKU 硬过滤、软偏好排序和分项解释。
2. 设计版本化 `ShoppingSessionState`，通过 owner/thread 隔离、字段 patch、候选过期和数据库 CAS 支持多轮预算修改、条件清空与候选排除，防止并发旧请求覆盖新状态。
3. 构建 pgvector 与关键词召回的混合 RAG，通过 RRF、候选商品范围、政策适用性和证据状态控制检索结果，使价格和库存始终以结构化 Catalog 为准。
4. 通过 Tool Gateway 与 PendingAction/HITL 隔离 Agent 建议和业务副作用，用户确认后才执行加购或偏好写入，并在执行前重新校验用户归属、参数和动作状态。
5. 实现 Checkout—Order—Inventory Reservation—Mock Payment—Outbox 交易链路，利用签名快照、幂等请求、PostgreSQL 行锁、支付恢复中间态和事务 Outbox 处理超卖、重复请求及发布失败。

实际简历建议保留 4 条。偏 Agent 岗保留第 1～4 条，再把第 5 条缩短；偏 Java/Python 后端岗保留第 1、2、4、5 条，把 RAG 并入推荐描述。

## 九、哪些内容不要夸大

- 支付是 Mock Provider，不是真实支付宝或微信支付。
- 多 Agent 默认是同一后端进程内协作，不是已经部署的分布式 Agent 微服务。
- SSE 主要发送运行阶段事件，不是完整的逐 token 模型流。
- RAG 降低无依据回答风险，但不能宣称完全消除幻觉。
- Outbox 是至少一次发布，Consumer 和 Inbox 尚未实现。
- 当前有合成评测和本地集成测试，不能宣称已有真实线上转化率、百万用户或 SLA。
- 10 类商品是 10 套品类定义，不代表每类都有大规模真实商品和同等质量数据。

## 十、记住项目的核心主线

如果前面的细节一时记不住，只要先记住下面这句话：

> **ShopMind 先用 Agent 理解用户想买什么，再用数据库和确定性规则决定哪些 SKU 真的满足要求；任何写操作都要用户确认，确认后再用数据库事务保证订单、库存和支付的一致性。**

整套项目围绕三件事展开：

1. **推荐要可信**：结构化约束、Catalog 真值、RAG 证据和可解释排序。
2. **Agent 要可控**：只读权限、Tool Gateway、运行预算和人工确认。
3. **交易要可靠**：幂等、行锁、库存预占、支付恢复和 Outbox。

能把这三条讲清楚，就已经能说明白这个项目。
